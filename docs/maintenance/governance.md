# 分支与文档治理规范

> 状态：当前治理规则。最近核对：2026-10-23（UTC+8）。适用于 `Martin-soaring-dev/bili-fav-organizer`。

## 1. 权威来源

- 当前长期代码主线只有 `main`。
- 当前版本事实以 [版本台账](version-ledger.md)、Git tag、GitHub Release 和构建运行相互核验为准。
- 当前发布操作以 [发布操作流程](../release-process.md) 为准。
- 旧维护计划、审计报告、测试日志和验收报告是历史证据，不因仍留在仓库就自动成为当前规则。
- 文档总入口是 [docs/INDEX.md](../INDEX.md)。

## 2. 分支规则

### 长期分支

- 仅保留 `main` 作为长期分支。
- 不再创建长期的 `master`、`gh-pages`、维护分支或验收分支；GitHub Pages 使用 `main` 的 `/docs`。
- 发布版本通过不可变 tag 标识；不得移动、重写或复用已发布的版本 tag。

### 短期分支命名

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `fix/` | 缺陷修复 | `fix/sqlite-wal-lifecycle-YYYYMMDD` |
| `feat/` | 新功能 | `feat/scan-diagnostics` |
| `docs/` | 文档治理 | `docs/release-process-refresh` |
| `test/` | 测试和验收基础设施 | `test/release-contracts` |
| `maintenance/` | 构建、依赖和维护性工作 | `maintenance/dependency-audit` |

分支名称应体现目标，不应只使用日期或随机 SHA 作为唯一语义。

### PR 与合并

- 除紧急恢复外，所有代码、工作流、发布规则和治理文档变更均从短期分支通过 PR 合入 `main`。
- PR 必须说明目的、影响范围、验证命令与结果、相关 Issue，以及是否影响用户文档、发布包或数据迁移。
- 合并后删除已合并短分支；验收分支只有在证据完成归档、脱敏和哈希核验后才可删除。
- 不使用 force push 改写已共享分支历史；不直接删除 `main`。
- 对 `main` 应启用 PR 合并、CI 必须通过、禁止强制推送和删除等保护。若仓库设置权限不可用，标记为管理员待办，不得声称保护已经配置。
- 自动删除已合并分支应开启；该设置不能代替验收证据归档。

## 3. 验收证据归档

每个正式验收记录必须包含：

- 被测 commit SHA 与 tree SHA；
- 操作系统、运行环境和必要的依赖版本；
- 实际执行的命令、退出码、测试总数及 PASS / FAIL / ERROR / SKIP；
- 日志、截图、构建产物 SHA-256 和报告之间的对应关系；
- 尚未验证的范围、阻塞项和人工步骤。

执行规则：

1. 原始测试结果不覆盖；修订报告必须保留修订记录，并区分原始材料与脱敏副本。
2. **不将旧提交的 PASS 转记到新提交。** 每份结果都必须明确绑定实际被测 SHA。
3. 将验收分支并入主干前，逐个检查文本与图片。绝对用户目录、个人标识、Cookie、token、真实收藏数据和其他私密信息必须脱敏。
4. 脱敏后生成清单，记录来源分支 / commit、归档文件、原始 blob SHA、脱敏操作和复核状态。若修改了文件内容，必须同时记录归档版本的校验值；不能用原始文件哈希冒充脱敏副本哈希。
5. 只有当报告、日志、截图和清单均已归档、链接有效、公开信息检查通过，才允许删除来源验收分支。
6. 若某类证据暂不能安全公开，应明确标记为 withheld / 待脱敏，保留来源并记录阻塞原因；不能把不完整归档宣称为完整验收。

## 4. 文档生命周期与结构

每份重要技术文档必须明确其状态、核对日期、适用版本 / commit 和证据来源。采用以下状态：

- **Current**：当前规则或当前事实，必须持续维护；
- **Draft**：尚未批准，不可作为执行依据；
- **Historical snapshot**：保留当时状态，不能作为当前状态；
- **Superseded**：已被明确的新文档取代，保留以供追溯。

职责分区：

- 用户文档：根 README、快速上手、发行包说明和 PDF；
- 版本与发布：版本台账、发布流程、Git tag / Release / Actions 证据；
- 长期规则：本文件；
- 设计与架构：`docs/design/`；
- 测试和证据：`docs/testing/` 与 `docs/testing/evidence/`；
- 历史审计：以日期 / commit 为锚点，并链接当前替代文档；
- `docs/index.html`：GitHub Pages Delivery Console，不替代 Markdown 文档目录。

避免把所有内容塞进单一的版本治理文件。历史报告不删除其失败结论；用状态横幅和替代链接防止旧状态被误读。

## 5. 发布一致性

发布前必须核对：

- Git tag、版本台账和 README 更新日志；
- GitHub Release 标题、正文、发行附件及 SHA-256；
- 安装包、便携包、Electron 包的版本和构建来源；
- 在线快速上手指南与 `output/pdf/快速上手.pdf`；
- CI、Windows 构建、安装 / 升级验收与公开 Pages 内容。

手动运行发布工作流使用所选分支 / ref 的源码，不应误认为它自动构建输入 tag 的源码。重建已有版本可能覆盖同名发行附件，必须在操作前明确确认。

## 6. Pages 与公开信息

- Pages 源为 `main` 的 `/docs`；不再依赖单独的 `gh-pages` 长期分支。
- Pages 变更必须检查页面是否可加载、相对链接、移动端基本布局，以及是否泄露本地路径、私人数据或内部信息。
- 工作流成功只证明部署步骤成功，不自动证明页面内容和隐私审查通过。
- 公开看板中的状态必须链接到可追溯的源文档或验收报告。

## 7. 维护完成定义

治理任务只有同时满足以下条件才算完成：

- 改动已提交到短期分支，并通过相应 CI / 链接和内容检查；
- PR 已合并到 `main`；
- 需要的验收证据已归档并绑定准确 SHA；
- 合并后的文档链接和 Pages 入口已复核；
- 已合并短分支已清理；受限的 GitHub 管理操作已明确记录为未完成，不得假报成功。
