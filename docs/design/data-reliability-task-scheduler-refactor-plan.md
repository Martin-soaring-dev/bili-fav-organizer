# Bili-fav-organizer 数据可靠性与统一任务调度架构重构计划

**版本：** 1.1（设计闭环稿）  
**日期：** 2026-10-12  
**状态：** 设计文档，尚未进入代码实施  
**适用基线：** 当前仓库 `main`（v0.209 稳定版）  
**本轮改动：** 仅新增本计划文档，不修改业务代码、数据库格式或发布配置。

## 1. 目标与边界

本轮重构解决四类可靠性问题：数据库缺失或损坏时不得静默出现空库；锁定、迁移和导入期间始终保留可验证的数据副本；后台任务能在明确检查点暂停并恢复；B 站写入结果不确定时不得盲目重发。

本轮是一次可靠性重构，不是密码学升级。目标架构由三个协作的核心模块组成：

1. **Database Lifecycle Manager（数据库生命周期管理器）**：控制数据库身份、初始化、连接准入、校验、快照、迁移、备份、恢复及文件切换。
2. **Unified Task Scheduler（统一任务调度器）**：统一管理长任务的创建、排队、运行、暂停、恢复、取消、检查点和异常恢复。
3. **Vault Manager（保险库管理器）**：保留现有密钥与加密方案，负责身份验证、密钥可用性和与任务/数据库生命周期的安全协调。

扫描、分析、画像、收藏夹整理及后续数据源能力通过统一接口使用这些基础设施。实施时允许先用适配器承接旧函数，不要求一次完成目录拆分。

### 1.1 已冻结的设计决策

| 主题 | 决策 |
|---|---|
| 业务数据库 | 保留 SQLite |
| 数据库加密 | 保留现有 AES-GCM 整文件加密及认证校验 |
| 密钥体系 | 保留现有 DEK/KEK、密码、恢复码和 Windows Hello 体验 |
| SQLCipher | 不采用 |
| 更改密码 | 只更新现有密钥包装，不重新加密整个业务数据库 |
| 数据库创建 | 只有显式的首次初始化流程可以创建 |
| 普通连接 | 缺失数据库时必须失败，禁止 SQLite 隐式建库 |
| 调度器 | 必须统一；第一版仅支持单进程调度器所有者 |
| 任务并发 | 第一版维持现有长任务的保守并发，不主动扩大并发 |
| 锁库 | 采用模式 B：请求锁定后暂停任务、排空访问、验证加密快照、清理应用工作明文，再报告锁定成功 |
| 结果优先级 | 数据一致性和不丢失优先于任务连续性或节省 API/Token |
| 远端写操作 | 请求发送前持久化操作意图；结果未知时先核对，禁止盲目重试 |
| Schema 变更 | 只对候选副本做版本化迁移；通过验证后才切换 |
| 业务导入 | 与整库恢复分离；JSON 导入不得复用覆盖数据目录的路径 |
| 当前工作方式 | 本文完成设计闭环；后续代码实施按小 PR 和阶段验收推进 |

### 1.2 不纳入本轮范围

不引入 SQLCipher，不重写业务算法，不更换前端框架，不做多进程或分布式任务调度，不把所有短时请求都包装成长任务，不加密全部应用配置，也不承诺对 SSD、文件系统快照或设备级取证进行安全擦除。

Python 运行时无法可靠保证把所有内存中的 DEK 副本清零。应用锁的可验证目标是撤销业务访问、关闭连接并丢弃应用持有的密钥引用；它不能替代系统磁盘加密。

## 2. 不可违反的数据安全约束

| 编号 | 不变量 | 验收含义 |
|---|---|---|
| I-01 | 不允许静默创建空库 | 已初始化库缺失、身份冲突、校验失败或无法解锁时，业务 API 不进入初始化路径 |
| I-02 | 不覆盖唯一有效副本 | 加密、解密、迁移、恢复、导入均先生成候选、验证候选，再提交切换；保留回退依据 |
| I-03 | 数据库访问集中授权 | 业务模块不得自行创建、替换、删除、关闭主数据库文件或绕过连接门禁 |
| I-04 | 暂停具有持久检查点 | 检查点及已完成业务结果原子提交；恢复时已确认完成的工作不重复写入 |
| I-05 | 远端未知写入不盲重试 | B 站结果不明的操作进入核对状态；核对前阻止可能冲突的后续写操作 |
| I-06 | 状态必须真实 | UI 遮蔽、任务暂停、数据库排空、快照加密完成、明文清理完成和已锁定分别表达 |

任何阶段若无法证明相关不变量，不得进入依赖该能力的后续阶段；稳定发布不得带有未解决的 P0 数据安全缺陷。

## 3. 现状与目标边界

当前关键实现集中在 `store.py`、`server.py`、`bili_api.py` 和 `static/app.js`。现有 SQLite 事务、扫描暂存、AI 结果持久化、远端写入 `unknown` 状态、AES-GCM 校验和迁移测试应被复用和强化。

| 当前区域 | 改造目标 |
|---|---|
| `store.py` | 将业务仓库接口与数据库生命周期、连接创建和文件操作分开 |
| `server.py` | 将分散线程及内存态任务迁到统一调度器；旧 API 暂时保留为适配入口 |
| 锁库与解锁 | 通过暂停屏障、连接排空、生命周期日志和候选文件协议协调 |
| ZIP 整包导入 | 改为隔离区解包、格式及身份校验、恢复点保护、受控切换 |
| 自动备份 | 从单份/未验证保留改为可验证恢复点和明确保留规则 |
| `bili_api.py` | 将每类远端写操作纳入稳定操作 ID、操作日志与专用核对器 |
| `static/app.js` | 任务状态从持久化记录读取；SSE 只负责实时推送 |

建议的目标目录仅是边界参考，初期可用适配器承接旧实现：

| 模块 | 职责 |
|---|---|
| `core/database/` | 生命周期、连接门禁、身份/完整性校验、备份、恢复、迁移 |
| `core/scheduler/` | 状态模型、注册表、单进程所有权、资源、检查点、崩溃恢复 |
| `core/vault/` | 保险库与数据库/调度器协调 |
| `tasks/` | 六类业务 worker；调用受控存储，不自行管理数据库文件 |
| API 层 | 注册现有兼容路由及后续任务中心路由 |
| 存储层 | SQLite 业务记录、任务、检查点、远端操作日志 |

## 4. Database Lifecycle Manager

### 4.1 数据库生命周期状态

| 状态 | 含义 | 普通业务访问 |
|---|---|---|
| `UNINITIALIZED` | 未发现既有身份；等待用户显式新建 | 否 |
| `OPENING` | 正在验证、解密或恢复 | 否 |
| `READY` | 身份、Schema 和完整性检查通过 | 是 |
| `DRAINING` | 关闭新准入，等待已准入请求收尾 | 仅已准入请求可完成 |
| `SEALING` | 正在生成、验证并提交加密候选 | 否 |
| `LOCKED` | 密文已验证、应用工作明文已清理、连接已关闭 | 否 |
| `RECOVERY_REQUIRED` | 有文件/身份/事务状态异常，等待恢复判断 | 否 |
| `FATAL` | 无安全自动恢复路径 | 否 |

Vault 认证、数据库生命周期和任务生命周期分别建模。密码验证成功不等于数据库有效；界面已遮蔽不等于数据库已关闭；任务已暂停也不等于加密已提交。

### 4.2 身份、首次初始化与冲突判据

使用三类非等价证据交叉判断：

| 证据 | 保存位置 | 用途 |
|---|---|---|
| `database_id`、Schema、提交代次 | SQLite 元信息及加密快照认证元数据 | 识别业务库身份和版本 |
| 当前快照指针、已提交代次、进行中事务摘要 | 库外轻量状态文件/事务日志 | 启动时识别生命周期事务阶段 |
| DEK 包装、Vault 初始化状态 | 现有 `vault.json` | 判断密钥身份与解锁入口 |

库外状态文件不得保存业务数据或解密密钥。它是恢复证据之一，不是脱离数据库身份、Vault 元数据和备份校验的唯一依据。

首次初始化必须由用户明确选择“新建保险库”并确认。即使检测不到任何文件，也不由普通启动自动建库。若数据库、Vault 元数据、Manifest、旧版数据或备份任一项显示曾初始化，而活动库缺失，进入 `RECOVERY_REQUIRED`。若所有相关证据一并被删除，程序无法证明历史上曾初始化，因此显式初始化动作是必要边界。

| 启动证据 | 决策 |
|---|---|
| 无既有证据，用户尚未确认新建 | 等待显式初始化 |
| 有有效密文、无工作明文 | 等待解锁 |
| 曾初始化但活动库缺失 | 阻止初始化，进入恢复 |
| Manifest 丢失但库/Vault/备份仍存在 | 保留文件并验证身份后恢复；不视为首次安装 |
| 明文与密文同时存在 | 依据身份、generation 和事务日志核验；不按时间戳选副本 |
| database ID、generation、Schema 或密钥包装冲突 | 保留各副本，阻断业务，进入人工恢复 |
| 密文损坏但有经恢复演练验证的备份 | 提示选择恢复点；保留原密文 |
| 密文损坏且无有效备份 | `RECOVERY_REQUIRED`，不得建新库 |
| Schema 高于当前支持版本 | 拒绝写入及降级，保留文件 |
| 任务检查点损坏 | 保留业务库；仅隔离对应任务并阻止其自动运行 |

### 4.3 普通连接门禁

普通读取使用禁止创建文件的只读连接；普通读写使用禁止创建文件的读写连接（SQLite URI `mode=ro` / `mode=rw` 或等价实现）。只有显式初始化入口可用创建权限。

连接检查和准入关闭必须通过同一生命周期门禁协调，避免“检查时允许、连接前已锁定”的竞态。连接管理记录活跃读写事务、持有者（API 请求或任务）、准入状态和关闭结果。全局锁顺序必须成文；任何数据库事务内禁止等待远端网络请求。

文件切换、迁移、整库恢复等维护操作必须独占维护权限。统一调度器完成前，使用临时维护门禁确保旧线程和 API 请求无法并发访问；不可在旧工作仍持有连接时替换数据库。

### 4.4 提交代次与库外生命周期事务日志

每次成功提交数据库快照或数据库级变更使用严格单调递增的 `generation`。新候选的 generation 为已验证源的 generation + 1。SQLite 元信息、加密候选认证元数据和库外状态文件必须能相互校验。

对数据库加密、解锁、迁移、整库导入和恢复，使用库外可恢复的生命周期事务日志。日志至少包含：

- `operation_id`、操作类型、`database_id`。
- 源/目标 generation、Schema 版本、文件标识与哈希。
- 候选路径/快照 ID、操作阶段、更新时间及失败原因。
- 需要时关联的任务和未核对远端操作 ID。

阶段为 `PREPARED → CANDIDATE_VERIFIED → COMMITTED → CLEANUP_COMPLETE`。状态文件和日志均通过同卷临时文件写入、刷新后原子替换；候选文件验证完毕前不触碰源文件。提交点定义为：候选通过身份和完整性验证后，原子更新库外已提交快照指针/代次。旧有效副本至少保留到新指针提交且后续恢复校验成功。无法唯一确定提交点时保留所有文件并请求人工恢复，禁止按 mtime 推断。

### 4.5 快照、加密与候选切换

在维护门禁关闭新请求、已准入事务排空后，使用 SQLite Online Backup API 生成一致性快照。不能在活动 WAL 数据库上只复制主 `.db` 文件。必要时按策略完成 WAL checkpoint 并关闭所有连接。

候选快照开放前需通过以下验证：

1. AES-GCM 认证完整，或解锁后的候选成功通过同一认证链。
2. SQLite `integrity_check` 通过；`foreign_key_check` 及指定业务不变量通过。
3. `database_id`、generation、Schema 与来源记录一致。
4. 数据库关键表数量/校验摘要符合迁移或恢复预期。
5. 密文/解密候选文件大小、哈希与事务日志所载一致。

加密失败、验证失败、磁盘空间不足或 Windows 文件占用时，保留现有有效副本并如实返回失败。只有候选验证并提交后才能进行清理。清理失败不能报告 `LOCKED`。

### 4.6 数据库连接、锁定与恢复

解锁流程：验证密码/恢复码 → 验证密文认证 → 解密到隔离候选 → 校验身份、generation、Schema、SQLite 完整性和业务不变量 → 通过门禁切换为活动库 → 数据库转入 `READY` → 调度器读取和校验任务检查点。

加密/解密临时文件、明文数据库、WAL、SHM、应用管理的 plain backup 均按事务日志识别。正常锁定只有在数据库访问已关闭、工作连接释放、有效密文提交、工作明文清理完成、Vault 撤销业务密钥引用后，才能报告 `LOCKED`。

任何事务日志与副本证据无法交叉验证时，保持业务关闭，保留全部候选文件，进入恢复界面；不自动修复、不自动删文件、不自动建库。

## 5. 备份、迁移与导入契约

### 5.1 备份类型与保留策略

| 类型 | 时机 | 用途 |
|---|---|---|
| 升级前整库恢复点 | Schema/数据格式升级前 | 版本回退和迁移恢复 |
| 高风险操作恢复点 | 全库导入、清理、大规模结构变更前 | 人为操作恢复 |
| 用户手动导出 | 用户明确请求 | 跨设备迁移与离线保存 |
| 业务 JSON 导出 | 用户请求 | 只导出业务记录，不视为整库备份 |

整库恢复点包含格式版本、database ID、generation、Schema、完整性信息和现有密钥包装/解密所需信息；按现有 AES-GCM 方案保护。每份恢复点须在隔离目录实际完成解密/SQLite 校验后，才能标记为“已验证可恢复”。

在容量允许时至少保留最近两个已验证恢复点；绝不删除最后一个已验证恢复点。若空间不足而无法建立新的恢复点，阻止破坏性迁移/替换并提示用户处理空间或备份问题。

### 5.2 导入隔离与类型区分

业务 JSON 导入是受校验的记录导入/合并，不能覆盖数据目录，也不能冒充完整数据库恢复。

整库恢复是独立流程：用户明确选择恢复点并确认替换 → 创建当前库恢复点 → 隔离解包 → 检查格式、身份、Schema 和完整性 → 形成候选库 → 提交切换 → 验证后才开放业务。失败时活动库保持不变。

ZIP 在隔离区解析，拒绝路径穿越、绝对路径、符号链接、重复关键文件、压缩展开超限、CRC 错误、未知格式及身份不匹配。任何拒绝场景均不能改写活动目录。

### 5.3 迁移和回退

Schema 迁移仅在候选副本上运行；事务化步骤使用事务。候选验证通过后再按生命周期提交协议切换。失败保留原库，不删表重建。

至少覆盖 v0.208 JSON/SQLite 历史迁移、v0.209 当前 SQLite、保险库启用/未启用、密码/恢复码解锁、旧 JSON 导入、传统 Windows 包装与 Electron Neo。对于高于当前版本支持的 Schema，拒绝读写、不尝试降级。旧程序能否打开新 Schema 必须经兼容测试证明；否则通过迁移前恢复点回退。

## 6. Unified Task Scheduler

### 6.1 任务状态与语义

建议任务状态：`QUEUED`、`RUNNING`、`PAUSING`、`PAUSED`、`RESUMING`、`CANCELLING`、`CANCELLED`、`INTERRUPTED`、`NEEDS_RECONCILIATION`、`COMPLETED`、`FAILED`。

| 状态 | 可验证条件 |
|---|---|
| `RUNNING` | 工作器真实持有调度准入与资源许可 |
| `PAUSING` | 收到暂停信号，仍可能有网络请求、事务或收尾步骤 |
| `PAUSED` | 检查点已持久化；工作器退出、连接/资源已释放；无待核对远端副作用 |
| `RESUMING` | 正校验检查点、输入签名、版本和资源 |
| `INTERRUPTED` | 重启时发现进程非正常结束；校验前不得直接继续 |
| `NEEDS_RECONCILIATION` | 存在未确认远端副作用；冻结冲突写操作 |
| `COMPLETED` | 业务结果和终态已原子持久化 |
| `CANCELLED` | 不再自动恢复；若遗留未知副作用，仍保留核对阻塞 |
| `FAILED` | 不可自动恢复或策略禁止重试 |

用户手动暂停和保险库暂停均保存 `pause_reason` 与恢复意图。手动暂停解锁/重启后不自动恢复；因保险库锁定暂停且检查点有效的安全任务，在解锁通过后才按策略自动恢复。取消与暂停不是同一种状态，取消不得在解锁后复活。

### 6.2 第一版所有权、资源和幂等

第一版只允许一个调度器进程拥有任务执行权。通过进程锁或等价机制拒绝第二个 owner；每次 owner 获取递增 fencing token/epoch。旧 worker 持有的过期 token 不得提交晚到检查点或写入任务状态。

长任务默认保持当前保守并发。资源规则：

| 资源 | 第一版规则 |
|---|---|
| 数据库写事务 | 短事务；不持事务等待网络 |
| B 站写操作 | 同一账号串行；统一限流 |
| B 站读操作 | 由调度器按现有安全限流控制 |
| AI Provider | 按 Provider/模型并发和速率配置控制 |
| 数据导入、迁移、锁库 | 独占维护/生命周期权限 |
| 未核对远端操作 | 阻止同账号冲突写操作，直到核对 |

现有启动 API 适配器必须处理重复请求：使用请求幂等键，或对同类型、同范围的活动任务返回既有 `task_id`，不得产生两个重复实例。

### 6.3 任务记录、worker 与检查点

每项任务持久化 `task_id`、类型、任务/检查点 Schema 版本、状态、参数、进度、checkpoint、错误类别、重试策略、尝试次数、pause reason/恢复意图、owner epoch、资源键、创建/更新时间。

检查点至少记录已提交的稳定业务 ID、输入/配置签名及版本。AI 任务还记录模型、供应商、参数、提示版本、分析范围；写任务记录用户确认的计划摘要及稳定操作 ID。业务结果、本地进度和检查点在同一个 SQLite 事务中提交，UI 进度以持久化记录为准，SSE 只推送变化。

检查点 Schema 不兼容、输入签名失效或 owner epoch 过期时，阻止自动恢复并显示原因；禁止用空检查点覆盖旧状态。单个任务检查点损坏不应使整个数据库失效。

Worker 提供统一能力：输入校验、执行、暂停请求、安全边界、持久化检查点、取消、结果核对和恢复验证。不是每个任务都需独立常驻线程。

### 6.4 统一调度器的范围

调度器须支持任务创建/排队/启动、暂停/继续/取消、持久状态查询、资源互斥、进程所有权、恢复判断、统一事件/日志、超时/退避策略和操作核对入口。暂不扩展当前长任务的并发能力。依赖关系未明确前，不并行启动互相影响的扫描、AI、整理任务。

## 7. 六类业务任务迁移契约

| 任务 | 检查点边界 | 恢复和重复处理规则 |
|---|---|---|
| 收藏夹扫描 | 收藏夹级，分页点仅在远端游标/数量/索引边界可校验时保存 | 优先复用 `scan_stage`、`folder_scan_state`。检查点失效时仅重扫未完成夹；新结果先暂存，完整验证后替换完整快照 |
| AI 内容分析 | 每个已提交分析结果/稳定视频 ID | 结果和检查点原子提交；恢复跳过本任务已提交结果。force_all 仅在新建任务时定义范围，同任务恢复不重算已提交项；未提交在途请求可重发并提示潜在 Token 消耗 |
| 收藏夹画像 | 单收藏夹完成后 | 持久化画像及该夹 checkpoint 原子提交；验证输入版本和画像配置签名 |
| AI 合并建议 | 阶段级 | 保存画像版本、模型和参数签名；签名匹配则复用，不匹配重算阶段。首版允许安全边界重算整轮，不为省算力牺牲正确性 |
| 整理方案执行 | 每个经用户确认的稳定操作 | 先持久化方案摘要/操作清单，再逐项操作；每步核对及提交后才能进入下一步 |
| 收藏夹合并 | 每个视频和收藏夹操作步骤 | 移动、删除、建夹、改名、删来源夹均有稳定操作 ID 和独立核对器；只有确认所有视频到位后才允许删除来源夹 |

### 7.1 扫描恢复：当前实现到哪一级（Beta 冻结）

当前实现按**收藏夹级**恢复，页级检查点只用于诊断，**不承诺精确页级续扫**：

- 已完成且目录计数一致的收藏夹会被跳过，不重复读取；
- 未完成的收藏夹（含暂停/取消时正在读的那一个）会**从头重新读取**，实际可能从该收藏夹第 1 页开始；
- `scan_stage` 以 `(scan_run_id, media_id, resource_key)` 为键，恢复时是新 `scan_run_id`，因此不会复用上一轮的半页暂存；
- 页级检查点（`{"phase": "paged", "page": N}`）已随任务持久化，可供排查问题，但恢复逻辑目前不消费它；
- 重复读取是安全的：暂存按资源键去重、数量校验通过后才整体替换快照，不完整结果不会冒充新快照，未停稳的远端写入不会被重放（见第 8 节）。

界面与文档只表述「已完成夹不重复读取、未完成夹重新读取」，不得承诺页级精确续扫。

## 8. B 站远端写入一致性

### 8.1 操作状态

远端操作与任务状态分开持久化，操作状态为：

`PREPARED → DISPATCHING → CONFIRMED / REJECTED / NEEDS_RECONCILIATION`

核对状态再转为 `CONFIRMED`、`NOT_APPLIED` 或 `MANUAL_REVIEW`。`DISPATCHING` 必须在实际发送请求前提交。重启时遗留的 `DISPATCHING` 一律视为待核对。

每项操作记录操作 ID、任务 ID、账号、操作类型、目标对象、稳定视频 ID/夹 ID、期望前置和后置状态、请求参数摘要、远端响应、当前本地提交结果、核对结果与时间。敏感 Cookie、令牌和完整密钥不得写入操作日志。

### 8.2 发送与核对规则

1. 生成稳定操作 ID，持久化操作意图及预期状态。
2. 提交 `DISPATCHING` 后才发送请求；网络请求期间不持有 SQLite 事务。
3. 收到结果后持久化远端响应并原子提交可确认的本地结果和检查点。
4. 超时、断连、响应丢失、响应后本地提交失败或进程异常退出，均进入核对。
5. 使用该接口专属后置条件核对：例如视频是否已在目标夹、来源夹是否仍保留、建夹名称/ID 是否可唯一定位。不能只看夹数量。
6. 仅在证明操作未生效且前置状态仍有效时允许再次发送，并复用原操作 ID；不确定时进入人工处理，不生成新 ID 绕过保护。

B 站接口不一定支持幂等键，因此不宣称严格 Exactly-once。目标是：不盲目重发，可验证时自动核对，无法验证时要求人工处理。同账号未核对操作会阻塞可能冲突的后续写任务。

## 9. 模式 B：保险库锁定、解锁与崩溃恢复

### 9.1 三层状态及锁定成功条件

前端可遮蔽状态、数据库状态和任务状态独立记录。Vault 协调状态建议为 `UNLOCKED → LOCK_REQUESTED → DRAINING → SEALING → CLEANING → LOCKED`，失败/卡住时为 `LOCK_BLOCKED` 或 `RECOVERY_REQUIRED`。

只有以下条件全满足才可报告 `LOCKED`：

- API 和调度器的新业务准入均已原子关闭；UI 已立即遮蔽。
- 已准入请求收尾；任务进入可验证暂停/核对状态，检查点持久化。
- 所有工作器退出，连接和事务关闭，维护门禁确认无写入者。
- 一致性快照及其加密候选通过身份、代次和完整性验证，并按生命周期协议提交。
- 应用工作明文数据库、WAL、SHM 和 plain backup 清理完成。
- 数据库门禁已关闭，业务不可再访问，Vault 已撤销其业务密钥引用。

### 9.2 锁定时序

| 阶段 | 动作 | 成功证据 |
|---|---|---|
| T0 | 接收锁定请求、遮蔽界面 | UI 显示“正在安全锁定”，服务端仍报告实际状态 |
| T1 | 原子关闭 API/调度器/数据库新准入 | 新业务请求明确拒绝 |
| T2 | 请求所有任务安全暂停 | 无新业务工作启动 |
| T3 | 完成在途操作，未知结果写入核对状态 | 无未登记远端副作用 |
| T4 | 提交检查点和操作日志 | 同库事务提交成功 |
| T5 | 等待工作器、请求、事务和连接全部退出 | 引用计数为零，无活跃写事务 |
| T6 | 通过 SQLite 一致性备份生成候选快照 | 身份/代次/Schema/SQLite 校验通过 |
| T7 | 加密并验证候选密文 | GCM 认证及候选元数据匹配 |
| T8 | 按指针/代次协议提交密文，保留旧有效副本 | 库外事务日志进入 `COMMITTED` |
| T9 | 清理应用工作明文和侧文件 | 清理列表完成，日志为 `CLEANUP_COMPLETE` |
| T10 | 关闭访问并撤销业务 DEK 引用 | Vault 与数据库状态均为锁定 |

UI 不得在 T0 之后把“正在锁定”提前显示为“已加密”。网络请求无法结束时不强杀可能仍有副作用的线程；超时仅用于诊断和显示阻塞原因，不能当作完成条件。

### 9.3 失败和异常退出恢复

锁库事务日志在数据库之外，程序启动时优先关闭业务准入，再判断副本和阶段。

| 失败位置 | 恢复动作 |
|---|---|
| 候选快照生成前 | 保留原库；重新校验后可重试 |
| 候选快照/密文生成或验证失败 | 保留原库和旧密文，隔离无效候选 |
| 候选已验证但未提交 | 不改变已提交指针；保留/隔离候选，按日志重试或回退 |
| 密文提交后明文未清理 | 继续保持业务关闭；验证已提交密文后继续清理 |
| 明文/WAL/SHM 清理失败 | 不报告 `LOCKED`；显示具体残留，进入收尾或恢复 |
| 事务日志与文件身份/代次冲突 | 保留所有副本，进入人工恢复，不按 mtime 选择 |
| 数据库有效但单个检查点损坏 | 保留业务数据，隔离任务、禁止其自动执行 |
| 网络写操作状态未知 | 任务进入核对；同账号冲突写任务继续阻塞 |

解锁时先验证凭据和密文，再解密到隔离候选。只有候选验证、身份比对及切换完成后才进入 `READY`。任务只在数据库 `READY` 后恢复；未知远端写入先核对。程序异常退出、强制结束或断电时不依赖 Python `finally` 完成持久化，所有关键阶段依靠库外事务日志和最后有效检查点识别。

## 10. API 与前端

先保留 `/api/scan`、`/api/analyze/start` 等现有路由，由其创建/查询统一任务并兼容旧前端。之后逐步增加：

| 接口 | 用途 |
|---|---|
| `POST /api/tasks` | 创建任务 |
| `GET /api/tasks`、`GET /api/tasks/{id}` | 查询任务列表和持久详情 |
| `POST /api/tasks/{id}/pause`、`resume`、`cancel` | 独立控制任务意图 |
| `GET /api/tasks/{id}/operations` | 查看关联远端写操作 |
| `POST /api/tasks/{id}/reconcile` | 启动或提交核对动作 |

前端任务中心展示任务/队列、持久化进度、暂停原因、锁库造成的暂停、解锁恢复结果、可重试性、历史错误及待核对操作。SSE 只承担即时通知；刷新或重连后从持久任务状态恢复。

## 11. 分阶段实施路线、交付物与退出门槛

每阶段通过门槛后才能开始依赖该能力的代码；阶段之间使用独立 PR，数据库格式、加密、备份、远端写入协议和前端显示不混在一个大 PR 中。

| 阶段 | 交付 | 退出门槛 |
|---|---|---|
| 0. 契约与盘点 | 任务/旧 API/所有远端写 API 映射；不变量追踪；状态、代次、日志、锁顺序、恢复规则冻结 | 六类任务、远端写接口均有 owner、资源、检查点、暂停/恢复/失败规则；每个 I-01 至 I-06 关联测试 |
| 1. 数据库准入 | 生命周期状态、显式初始化、普通连接门禁、database ID 和 generation 元信息 | 缺库普通连接拒绝且不建文件；重复初始化无覆盖；身份冲突/损坏阻断业务 |
| 2. 生命周期恢复基础 | 库外事务日志、一致性快照、候选验证、备份/恢复/迁移/隔离导入；旧任务运行期间使用维护门禁 | 每个提交点故障注入后能恢复到唯一已验证副本；旧库未丢；非法导入不改变活动数据 |
| 3. 调度器核心 | 单进程所有权、任务表、状态转换、资源和暂停屏障、幂等 API 适配、检查点版本 | 重复启动不生成重复任务；第二个 owner 被拒；旧 epoch 不能提交；手动暂停不自动恢复 |
| 4. 本地/AI 任务迁移 | 扫描、分析、画像、AI 合并建议 worker | 每项在结果提交前后退出/重启均有正确恢复；已提交项不重做；失效检查点不被伪装为新进度 |
| 5. 远端写入闭环 | 整理执行和收藏夹合并的稳定操作 ID、写前日志、专用核对器、冲突资源阻塞 | 每类远端写覆盖发送前退出、发出无响应、响应后提交失败、明确拒绝等场景；未知写入不重发 |
| 6. 模式 B 集成 | Vault/调度器/数据库的完整锁定和解锁屏障；锁定事务恢复；UI 状态 | 六类任务运行期间逐一锁库；仅全部锁定条件成立后报告已锁；各日志阶段杀进程恢复正确 |
| 7. Windows 与兼容验收 | 隔离用户目录、旧版升级、恢复码、传统壳与 Electron Neo 安装包/文件占用验证 | 受支持升级路径、恢复演练及真实打包形态均通过；WAL/SHM/残留明文语义正确 |
| 8. Beta/稳定发布 | 隔离目录 Beta、完整验收报告、迁移/恢复说明、已知限制 | 全部 P0 自动化和 Windows 验收通过，无未解决 P0/P1 数据安全问题后，才决定合并 main 和正式 Tag |

阶段 1/2 可先于统一调度器完成，但整库维护必须有可靠临时维护门禁；不能因调度器未迁完就允许旧线程并发访问被替换的数据库。阶段 4 与阶段 5 可在接口契约稳定后并行开发不同 worker，但都必须依赖阶段 3 的调度器 API；阶段 6 依赖数据库生命周期、调度器和远端操作协议全部验收。

## 12. 测试和发布验收

### 12.1 自动化与故障注入

| 分类 | 必测场景 |
|---|---|
| 首次初始化 | 首次显式新建、重复初始化、库/Vault/Manifest/旧版数据单独缺失 |
| 连接门禁 | 活动库缺失、权限不足、只读、锁定后请求、新请求与关闭门禁竞态 |
| SQLite 一致性 | WAL 有提交/未提交事务、连接未释放、快照/恢复/完整性检查 |
| 身份及加密 | 错误密码/恢复码、GCM 标签篡改/截断、ID/generation/Schema 冲突 |
| 生命周期日志 | PREPARED、CANDIDATE_VERIFIED、COMMITTED、CLEANUP_COMPLETE 前后强制退出 |
| 备份/迁移 | 磁盘不足、候选迁移失败、超前 Schema、恢复点淘汰边界 |
| ZIP 导入 | 路径穿越、符号链接、重复关键文件、压缩炸弹、CRC/格式/身份错误 |
| 任务调度 | 重复启动、两个 owner、过期 fencing token、手动暂停/锁库暂停、取消/重启 |
| 检查点 | 每项业务结果提交前后退出、版本不兼容、输入签名变化、检查点单独损坏 |
| AI 任务 | 在途请求、批次失败、force_all 恢复、Provider 限流和可能重复 Token 记录 |
| 远端写操作 | 发送前退出、发送后响应丢失、远端成功本地提交失败、明确拒绝、核对与人工处理 |
| Windows | 文件占用、WAL/SHM、非正常退出、两种桌面包装、目录迁移和真实安装升级 |

关键故障点必须验证数据来源、database ID、generation、Schema、逻辑记录核验、任务/操作状态和恢复路径。自动化测试不得使用真实 Cookie、API Key 或未经授权的 B 站写操作；真实远端行为只在明确隔离且用户可控的验收环境进行。

### 12.2 发布门槛

稳定发布前同时满足：

- P0 自动化用例全通过；P0 用例不得跳过；没有未解决 P0/P1 数据安全缺陷。
- 锁定/恢复每个持久化阶段至少做进程强制退出注入；没有空库替代、唯一副本覆盖、错误报告 LOCKED 或未知写入盲重发。
- 至少一个实际备份恢复演练在隔离目录成功；关键逻辑记录/身份/代次核验通过。
- 受支持的旧版迁移、密码与恢复码解锁、Windows 实际安装和文件占用场景通过。
- 明确记录无法测试的断电/硬件损坏风险，并提供用户可执行的备份/恢复说明。
- Release 说明列出兼容范围、恢复方法、已知限制和备份建议。

Beta 仅使用隔离数据目录和可恢复副本。Beta 不能覆盖唯一真实数据目录，也不能以“测试版”理由带入已知静默数据覆盖风险。

## 13. 不变量追踪矩阵

| 不变量 | 主要实现阶段 | 最低验收证据 |
|---|---|---|
| I-01 禁止静默空库 | 阶段 1、2 | 删除已初始化库后，普通 API 和启动流程均不建库 |
| I-02 不覆盖唯一副本 | 阶段 2、6 | 候选各失败点保留源副本；备份隔离恢复成功 |

| I-05 未知远端写不重试 | 阶段 5、6 | 断网/响应丢失后进入核对并阻塞冲突写，确认未生效才重发 |

## 14. 仍需实施前以真实源码核实的清单

下列事项不再改变本计划的架构方向，但在阶段 0 需要对照实际代码确认接口与迁移细节：

1. 逐项列出六类任务当前启动路由、线程/任务对象、停止信号、相关 SQLite 表和持久结果。
2. 盘点所有数据库连接创建点、初始化/迁移/备份/替换/删除点，确保没有隐式连接旁路。
3. 盘点每一种 B 站写 API 的请求、响应及可查询的后置状态；没有唯一核对条件的操作固定走人工复核。
4. 对现有 `vault.json`、加密容器、plain-backup、恢复码及 Windows Hello 元数据做格式兼容清单。
5. 明确 generation 的写入事务和库外状态文件字段，验证其原子替换/刷新行为符合目标操作系统。
6. 确认所有备份/导出包版本及敏感字段，明确恢复点与业务 JSON 文件的 UI 名称和含义。
7. 根据实际数据量和 Windows 安装目录评估两个已验证恢复点的空间需求；不足时仍不得删除最后一个有效点。

发现代码事实与计划冲突时，先更新接口映射和测试，不得弱化 I-01 至 I-06 来适配现状。

## 15. 最终交付状态

本计划完成的标志是：数据库生命周期、任务调度、远端操作和 Vault 锁定之间的状态、提交点、恢复依据、阶段依赖和发布门槛已有明确书面契约。当前文档完成这些设计闭环，但不代表任何实现阶段已经通过。

预期用户结果：

- 数据库文件缺失、损坏、身份冲突或迁移失败时得到明确阻断和恢复路径，不会悄悄看到空库。
- 扫描、分析、画像及整理任务的暂停、取消、异常重启和恢复都有可查记录。
- 锁定只有在工作排空、加密验证、密文提交和明文清理后才报告成功。
- B 站结果不明的写操作先核对，不会因重启或解锁盲目重复执行。
- 密码、恢复码、Windows Hello 和既有 AES-GCM 保险库使用体验保持兼容。
- 每个后续 PR 都能对应到不变量、验收用例、数据影响和回滚方法。

**路线：** 契约冻结 → 数据库准入 → 生命周期/备份恢复 → 统一任务调度器 → 业务检查点 → 远端写入核对 → 模式 B 集成 → Windows 验收 → Beta 与正式发布评审。
